# Tendon — Injury Risk Predictor

> **Learning project** — built as the CS 220 final project at Knox College. This is a student submission for educational purposes, not a production-ready or medically validated application. The risk scores and AI recommendations are not medical advice.

A fullstack web app where gym users log workouts and see an interactive human body avatar that color-codes each muscle group by current injury risk. AI-powered recovery recommendations are generated by the Gemini API, with a deterministic fallback when no API key is configured.

---

## What It Does

1. Register with email + password (or sign in if you have an account)
2. See a body avatar — all 16 muscle groups are color-coded from gray (no data) to red (critical) based on your recent training load
3. Log a workout: pick muscle groups, set RPE, duration, soreness, and optionally add per-exercise set rows
4. Click any muscle on the avatar to see its risk score and recommendation
5. Browse your full workout history, a 14-day risk trend chart, and a calendar view of training days
6. Write private training notes that persist with your account

## Environment Variables

Copy `.env.example` to `.env` at the project root. The only variable you must set locally is `AUTH_SECRET`.

```dotenv
# REQUIRED — sign tokens. Any long random string works locally.
AUTH_SECRET=replace_with_a_long_random_secret

# OPTIONAL — leave blank to run AI features in deterministic demo mode
GEMINI_API_KEY=
GEMINI_MODEL=gemini-2.5-flash-lite

# Local SQLite — no Turso account needed
TURSO_DATABASE_URL=file:tendon.db
TURSO_AUTH_TOKEN=

# Production Turso (Render deployment only)
# TURSO_DATABASE_URL=libsql://your-db-name.turso.io
# TURSO_AUTH_TOKEN=your-token-here

# Must point at the running backend
VITE_API_BASE_URL=http://localhost:8000/api
```

When `GEMINI_API_KEY` is blank, all `/api/ai/*` endpoints return deterministic demo responses instead of calling Gemini. Everything else works normally.

## Risk Scoring — How It Works

All risk math lives server-side in `server/risk.py`. The client only renders what the server returns.

### Step 1 — Session bump (load added per workout)

Each time a muscle group is trained, its cumulative load increases:

```
bump = (0.3 + (rpe / 10) × 0.6) × volume_factor

volume_factor = clamp(total_reps / 30, 0.5, 1.75)
             = 1.0  if no rep data is recorded
```

Where:
- `rpe` is the Rate of Perceived Exertion (1–10) for the session
- `total_reps` is the sum of all reps logged for that muscle group's set rows
- The load for each muscle group is capped at `4.0`

**Examples:**
- RPE 5, no rep data → bump = `0.3 + 0.5 × 0.6 = 0.6`
- RPE 10, no rep data → bump = `0.3 + 1.0 × 0.6 = 0.9`
- RPE 8, 60 reps → bump = `0.3 + 0.8 × 0.6 = 0.78`, then × `min(1.75, 60/30) = 1.75` → `1.365`

### Step 2 — Load to risk level

The continuous load float (0–4) maps to one of five discrete risk levels:

| Load range | Level | Color |
|---|---|---|
| `0` | `none` | Gray — no data |
| `0 < load < 1.0` | `low` | Blue |
| `1.0 ≤ load < 2.0` | `mod` | Amber |
| `2.0 ≤ load < 3.5` | `high` | Orange |
| `load ≥ 3.5` | `crit` | Red |

The displayed score (0–100) is `round(load / 4 × 100)`.

### Step 3 — Aggregate score

A single overall injury risk score across all muscles, peak-weighted so one critical muscle dominates:

```
active_loads = [load for load in all 16 muscles if load > 0]
aggregate    = min(100, round(avg(active_loads) × 12 + max(active_loads) × 14))
```

Returns `0` if no muscles have been trained.

### Step 4 — 14-day trend

For each of the last 14 days, the aggregate score is computed against all sessions up to and including that day, producing a time series used for the sparkline chart.

### Deterministic recommendations

Each muscle gets a text recommendation based solely on its risk level (no AI required):

| Level | Message |
|---|---|
| `none` | Has no recent training data. Log a session to start tracking. |
| `low` | Fresh and recovered. Good day to train at full intensity. |
| `mod` | Moderate fatigue. Light to moderate volume is fine; skip max-effort sets. |
| `high` | Elevated load. Drop volume by ~30% or take a rest day. |
| `crit` | Critically loaded. Rest at least 48–72 hours to prevent injury. |

## Authentication — How It Works

Passwords are hashed with **PBKDF2-SHA256** (200,000 iterations, random 16-byte salt). The hash format is:
```
pbkdf2_sha256$200000$<base64-salt>$<base64-digest>
```

On login, the server returns a **custom HMAC-signed Bearer token** — a lightweight JWT-like format:
```
<base64(payload_json)>.<base64(HMAC-SHA256 signature)>
```

The payload contains `{"sub": "<username>", "exp": <unix-timestamp>}`. Tokens expire after **12 hours**. The signing key is `AUTH_SECRET` from your environment. Every protected route verifies the token and additionally checks that the token's `sub` matches the URL's `username` parameter.

Usernames are derived automatically from the email address prefix (e.g. `jsmith@gmail.com` → `jsmith`), with numeric suffixes added if the name is taken.

Password reset uses a security question/answer flow. The security answer is also stored as a PBKDF2-SHA256 hash and compared in constant time.

## Database Schema

Three tables, managed by `server/database.py` which runs schema creation and additive `ALTER TABLE` migrations on every startup:

```sql
users (
    username             TEXT PRIMARY KEY,
    email                TEXT UNIQUE,
    first_name           TEXT NOT NULL DEFAULT '',
    last_name            TEXT NOT NULL DEFAULT '',
    password_hash        TEXT,
    gender               TEXT NOT NULL DEFAULT '',
    age                  INTEGER,
    security_question    TEXT,
    security_answer_hash TEXT
)

sessions (
    id       TEXT PRIMARY KEY,
    username TEXT NOT NULL REFERENCES users(username),
    date     TEXT NOT NULL,           -- ISO date string
    name     TEXT NOT NULL,
    groups   TEXT NOT NULL,           -- JSON array of muscle group IDs
    rpe      INTEGER NOT NULL,        -- 1–10
    duration INTEGER NOT NULL,        -- minutes
    soreness INTEGER NOT NULL DEFAULT 5,
    entries  TEXT                     -- JSON array of per-exercise set rows (nullable)
)

notes (
    username   TEXT PRIMARY KEY REFERENCES users(username),
    body       TEXT NOT NULL DEFAULT '',
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
)
```

## Troubleshooting

**Network error on load** — confirm the backend is running at `http://localhost:8000` and that `VITE_API_BASE_URL` in `client/.env` matches.

**`npm install` fails** — run it from inside `client/`, not the project root.

**Port conflict** — kill whatever holds port 5173 or run `npm run dev -- --port 3000`.

**AI endpoints return demo responses** — expected when `GEMINI_API_KEY` is blank. Set a real key in `.env` to get live Gemini responses.

**Schema errors on startup** — the server runs `ALTER TABLE` migrations idempotently; errors from columns that already exist are silently swallowed. If you hit unexpected schema issues, delete `server/tendon.db` and restart.

**"Invalid or expired session"** — tokens expire after 12 hours. Sign in again to get a fresh token.
